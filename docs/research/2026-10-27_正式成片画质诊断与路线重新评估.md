# MemoryRoom：正式成片画质诊断与路线重新评估

日期：2026-10-27。本文接续[阶段复盘](../MemoryRoom_截至2026-10-27_已完成阶段与尝试复盘.md)，取代[路线收敛](2026-10-27_路线收敛与分层架构决定.md)中基于 47074 失败记录做出的诊断。

本轮只读取了本地文件：原始采集包 `1ebc5b7a…capture.zip` 中的 `session.json`、正式成片 `final.ply` 的文件头、注册报告和引擎锁，以及采集 App 和查看器的源码。没有运行训练、测试、构建或浏览器，没有连接学校，也没有改代码。

## 一、结论

**OOOSplat 链路已经跑通，成片不达标的主要原因在输入素材，其次是训练容量，再次是查看器没有使用朝向信息。** 换训练器或换路线都解决不了这三个问题。下一步应在同一 OOOSplat 链路上只改输入，做一次对照。

分层组合架构（高斯背景 + 独立物品 + 参数化柜门 + 现有运行端）仍然成立，这个判断不变。变化的是优先级：先把背景素材质量提上来。

## 三、问题按影响排序

1. **输入分辨率和清晰度不够（影响最大）。** 2.8 MP，中位模糊约 3 px，每秒约 1 帧，这是“顺带记录的视频帧”，不是摄影测量素材。高斯只能还原图里有的细节，文字不清、表面发糊首先出在这里。
2. **视角少且集中。** 12 分钟只留下约 420 张可用图，站位范围不到 2 m。柜面、地面和远处家具缺少多角度清晰观测，于是出现缺洞和不自然的表面。
3. **训练容量偏低。** balanced 配方上限 100 万高斯，对一整间房偏少。不过素材不够清晰时，单纯加点数只会放大噪声，所以排在第三。
4. **朝向混乱是查看器的问题。** COLMAP 的世界坐标是任意的，Brush 已经估出竖直方向并写进 PLY 头，但查看器没有用。另一种做法是用 ARKit 位姿对 COLMAP 结果做相似变换对齐（COLMAP 自带 `model_aligner`），一次解决朝向、地面和米制尺度。两种做法都不更换 OOOSplat 引擎。
5. **采集负担大，但效率低。** 用户扫了约 12 分钟，平均每秒只存 1 帧。负担大不等于素材多。

## 四、下一步：同一链路，只改输入的对照实验

由用户执行。四组都走同一套 OOOSplat 配方，范围限定为同一个角落（桌子 + 柜子），并留出 5 张不参与训练的照片用于对比。

| 组 | 输入 | 要回答的问题 |
| --- | --- | --- |
| A（已有） | 现有 493 帧 ARKit 视频流 | 基线 |
| B | iPhone 原生相机 4K 视频：锁定曝光和对焦（长按 AE/AF 锁），慢速移动，约 2 分钟；抽帧时按清晰度挑选 | 换成高质量输入后画质能提升多少 |
| C | B 的素材 + 更高容量配方（OOOSplat 内更高质量档或更多高斯） | 训练容量还差多少 |
| D（可选） | 同一角落用 LCC Scan 或 Scaniverse Splat 扫一次 | 成熟产品在这个房间能达到什么水平 |

判断方法：

- **B 明显好于 A**：问题在采集。改采集 App，暂不换后端。
- **B 和 A 差不多**：问题在配准或训练，再看 C 和 D。
- **D 明显好于 B 和 C**：考虑把背景交给成熟产品（导出 PLY/SPZ），MemoryRoom 只做组合、交互和记忆。

## 五、对应的采集 App 改动（待 B 组结论后再做）

- 关键帧改用 `ARSession.captureHighResolutionFrame`（iOS 16+），并选择 `recommendedVideoFormatForHighResolutionFrameCapturing`，保留每帧的 ARKit 位姿。高分辨率帧的实际吞吐、发热和存储需要在 iPhone 17 Pro 上实测。
- 通过 `configurableCaptureDeviceForPrimaryCamera` 在开始扫描后锁定曝光、白平衡和对焦。
- 取帧条件从固定时间间隔改为“移动或转动足够距离，且预估模糊低于阈值”。
- 引导用户在房间里多换几个站位，而不是原地转圈；App 已有覆盖格，可以加一项“站位分布”提示。

## 六、架构层面的重新评估

| 层 | 原建议 | 现在的判断 |
| --- | --- | --- |
| 空间背景 | 3DGS | 不变。后端保留 OOOSplat，输入质量是第一优先；D 组结果好的话，接受成熟产品作为可替换后端 |
| 朝向与尺度 | 未单列 | 新增为独立任务：读取竖直轴或用 ARKit 位姿做相似变换对齐，在查看器导入时校正 |
| 可拿物品 | Apple Object Capture 网格 | 不变，仍是成本最低的独立物品方案；可与背景实验并行 |
| 柜门抽屉 | 参数化网格 + 人工确认门轴 | 不变 |
| 干净背景 | 先拍物品、移走、再扫背景 | 不变 |
| 运行端 | Spark + Three.js + SceneGraph | 不变。注意 236 MB 单个 PLY 已接近 256 MB 项目包上限，之后需要压缩为 SPZ 或启用 LOD |

## 七、需要用户决定的事项

1. 是否按第四节做 B 组对照（只换输入，引擎不变）。
2. 是否允许修改查看器导入，使用 PLY 头里的竖直轴或做 ARKit 对齐，以修复朝向问题。
3. D 组是否使用 LCC Scan 或 Scaniverse（免费，本机处理，不上传）。
