# MemoryRoom：AI房间重建推荐架构与分钟级目标评估

日期：2026-10-26。用户决定重点探索“真实扫描/照片约束AI制作可交互房间”，允许Agent与部分生成成本，希望普通用户操作少、等待尽量不超过几分钟，支持手机运行、拿取物品、柜门抽屉和记忆内容。本文为资料与代码接口审计、架构建议，不是已经跑通的新链路。

本轮使用AnySearch MCP检索13项，已提交反馈；主要正文通过Lightpanda（用户称QuickPanda）读取，未使用Kimi。arXiv的Lightpanda提取被阻时用内置工具读取论文。读取本地Scene Graph、provider接口、GLB导入及iOS采集字段，没有安装软件、调用生成API、上传房间、运行Blender/训练/测试，也没有改应用代码。

## 一、结论

建议近期主链为：

**手机RGB-D/RoomPlan与照片 → 证据规范化 → 结构化SceneSpec → 有预算的AI制作队列 → Blender资产编译/材质/导出 → 独立GLB与交互清单 → 现有Three.js/Spark工作台和手机网页。**

重点复用LiteReality-Agent的端到端架构，不再只围绕通用Blender MCP搭一堆无约束提示词。保留原始高斯作为视觉参考或可选背景；不要求全房间和所有物品必须同一种表示。不增加“先Unity渲染一次”作为网页发布前置步骤。

目前没有证据支持“任意整屋、接近展示片的高清程度、完整独立物品和关节、从提交到手机最终可用≤5分钟”的承诺。几分钟首版可作为受限范围/资产复用下的产品目标，不能把它冒充高清最终版已交付。如果用户把几分钟最终成片作为硬条件，当前这条路线应判为尚待证明。

## 二、这次新找到的对口工程

### 1. LiteReality-Agent：最值得优先审计复用

- [代码](https://github.com/LiteReality/LiteReality-Agent)
- [作者项目页和示例](https://litereality.github.io/agent/)
- [交互式结果浏览](https://litereality.github.io/agent/vr/index.html)
- [论文](https://arxiv.org/abs/2610.01863)
- [免费iOS采集App](https://apps.apple.com/gb/app/litereality/id6774158260)

当前公开README展示扫描到结构化房间、关节资产、布局/碰撞处理及Blender/GLB输出。主仓库Apache-2.0；不因此推断App源码、所有权重与素材库均同许可。

其最有用的设计是分开：确定性的采集→初始场景，与Agent进行的后续修改；制作中间表示可以重建，任务可恢复，重模型与运行位置分离。公开产物包括Room.blend、Room.glb及房间程序。代码还已有Claude/Codex provider边界，说明兼容多Agent有现实参考，而不是重新设计全部底层。

部署并非纯免费无依赖：作者要求Blender5.x、已登录Agent CLI，图片参考生成API，以及TRELLIS/GroundingDINO的GPU执行位置；本地GPU路线要求Linux/NVIDIA≥24GB。Mac可承担编排/Blender，重推理使用外部GPU。上游推荐Modal是其默认部署选择，不作为我们自动上传房间或新建云账号的授权；我们已有学校GPU，应优先评估独立Slurm worker，不能常驻登录节点做推理。

仓库提到的“每场景通常不到1美元”只针对参考图片生成，不包含Agent订阅/Token、GPU、渲染、排队、传输和重试，不能当整条链路总费用。

### 2. img2interior / plugin-interior：最贴近Blender到Three.js的制作工作流

- [当前仓库（旧img2interior重定向）](https://github.com/img2threejs/plugin-interior)
- [制作runbook](https://github.com/img2threejs/plugin-interior/blob/main/reference/production-runbook.md)
- [许可](https://github.com/img2threejs/plugin-interior/blob/main/LICENSE)

支持Claude Code、Codex、OpenCode式图像Agent；流程包含读参考、建立场景、渲染比较、制作材质/烘焙、导出和Three.js查看。适合参考“制作态与网页运行态分离”、材质交付、修订和资源来源记录。

但它是定制的Free Use/Restricted Commercialization许可、source-available，非OSI开源。可使用它制作商业输出与把工具商业化是不同权限，不能作为Apache模块随意整体复制进MemoryRoom产品。其示例也明确为特定研究场景，不是新用户任意照片都能一键同质量。本文只参考工作流思想，未安装/调用其skill。

### 3. MCP for Blender：操作桥，不是完整重建后端

[代码](https://github.com/ahujasid/mcp-for-blender)。可用于连接Agent和Blender执行Python/查看场景。它解决工具调用，不能自动提供精确几何、资产、材质和闭环验收。若采用后台bpy批处理，也不必把MCP作为所有制作步骤唯一通道。

### 4. 论文与评估工具：参考失败模式，不当生产流水线

- [LEGO-Anything](https://arxiv.org/abs/2609.36380)：把图片重建视为代码生成；研究强调初始化不准、修改破坏既有正确结果、自我评价不可靠。对我们有用的是证据约束与版本回退，而不是单纯增加推理轮数。本轮未确认其完整工程GitHub入口，不将论文当现成可安装组件。
- [BlenderGym-Open](https://github.com/richard-guyunqi/BlenderGym-Open)：多模型Blender操作评估参考，不是面向用户的整屋扫描App。

## 四、建议的架构分层

### A. Capture / Evidence：用户只拍一次，原件保留

接受自有iOS采集包、LiteReality Scanner原始包或其他含真实位姿/深度的输入。仅SPZ/PLY成品仍可作参考，但不能自动还原原始RGB-D信息。

统一`EvidenceBundle`：原图/清晰关键帧、相机内参、位姿、深度、跟踪状态、RoomPlan结构与物件候选、用户选定重点物品、空位/打开柜门等稳定片段、尺度和坐标来源。不要求用户手动挑188张；保存全部原件，Agent按房间/墙/物件读取相关视图。

结构、家具整体与小物件采用不同来源。小物件未识别时，允许点选/画框/输入名称和单独扫描；缺少底面、内部或背面时明确标未知，不用无依据细节伪装真实。

### B. SceneSpec：稳定的数据层

统一米制右手Y-up、原点、地面、初始相机、对象ID、层级、位置/旋转/尺寸、支撑关系、父容器、材质来源、关节轴/支点/行程、碰撞代理、证据与置信度、版本。区分实拍/生成/近似模板，不把相似资产当原物复制。

先把这个规范确定，Agent模型才可以替换。Blender的Z-up、OpenCV相机约定、glTF默认轴转换分别处理，避免重复翻转；关节、碰撞与相机必须随整体坐标变换同步转换。

### C. Agent / Planner：有限循环而非整屋从零自由写

规划器决定每个物件走哪条路：

- 墙地面、桌板、柜体：参数化生成器，尺寸来自证据。
- 重复椅子、把手：一个资产，多实例。
- 一般物品：已有真实资产/本地缓存/许可清楚的库资产。
- 重点回忆物件：独立扫描或近景重建。
- 无法取得准确资产：明确可选的图生3D生成，保留生成标记。

采用`AgentAdapter`接口：输入SessionSpec/任务、工具能力和预算；输出标准事件、场景补丁、资产与错误。提供Claude/Codex等适配器并允许后续扩展。接口兼容不保证模型输出等质量，必须声明image/tool/review/cancel/budget能力。

LiteReality当前文档已有provider差异；部分对象refinement被架构文档标为Claude-only，而其默认模型配置又将相关角色指向Codex，属于接入前需核对的文档/代码边界。不能承诺任意Agent接入后所有阶段无差别运行。

每次变更形成候选版本，保留上个可用版本；测量和几何规则约束放置。视觉critic辅助材质判断，不把“模型说好看”当唯一几何验收。限制修改轮数，超时留下明确状态，不标成功。

### D. AssetFactory / Blender Worker

确定性脚本负责创建/编译规范场景，Agent只在有必要时写局部几何或材质补丁。Blender用于模型制作、拆部件、UV/贴图与离线参考渲染；不让手机运行Blender，也不把Cycles图片/视频当自由漫游资产。

关节资产必须从建模时拆分：柜体、门板、抽屉、把手、内容分别有身份；背景不得残留要拿走物品的固定副本。动作可先采用已有简化关节，不要求第一版引入完整MuJoCo机器人动力学。

生成或检测重推理放独立GPU环境，Mac承担编排/建模可选；执行位置通过runtime适配，不污染现有OOOSplat环境。学校A40显存在容量上符合上游≥24GB门槛，但CPU30GB配额、依赖编译、队列与吞吐尚未实测，不能说已可直接运行。

### E. Packaging / Runtime

制作输出保留`.blend`源文件；运行输出为独立GLB/贴图、场景清单、关节与代理几何、相机、质量警告和来源。手机只取结果，后续浏览不持续消耗Agent Token。

优先现有Three.js手机网页，再考虑PWA与离线资产缓存；它们尚未因本次调研自动完成。不需要“Blender先渲染，再进Unity渲染”这条固定链路。Unity/UE5只在原生复杂物理、VR或引擎工作流确有收益时另作客户端；保持同一SceneSpec，不重做记忆数据。

静态环境光照可烘焙，活动门和物品保留适当动态照明/阴影；让网页与Blender按同一曝光/色彩目标匹配。离线宣传渲染不能代替手机运行画面。模型分级、贴图尺寸、实例复用和按需加载是性能控制，不等同必须换引擎。[glTF Transform](https://gltf-transform.dev/)可作后续资源处理工具，但压缩扩展需要与查看器解码能力一致。

## 五、如何接入我们现有项目

已读本地代码事实：

1. `packages/scene/src/schema.ts`已有独立节点、父子关系、transform、hinge/slide、pivot、记忆、附件、版本和资产provenance，后半程不必推倒。
2. provider接口已有提交/状态/取消/取资产，但目前枚举集中于旧高斯路线，尚无Blender-agent provider；新增应是独立provider，不把旧任务改名假装已接上。
3. 当前GLB导入把整文件作为一个资产/节点，`loadLocalGLB`主要返回场景，没有自动把上游关节、部件清单或MuJoCo数据映射到我们的节点。只拿`Room.glb`导入不能保证可拿取、可开门。应做结果适配器，导出独立物件或稳定内部路径，并生成MemoryRoom场景清单。
4. 当前GLB加载拒绝Draco、meshopt、KTX2等所列压缩扩展；先无压缩兼容输出，再单独接解码器。不能直接启用所有优化器后宣称现有网页支持。
5. 当前iOS代码的`room-layout.json`主要保存墙/地面；没有看到完整RoomPlan USDZ和家具表导出。LiteReality默认需要`room.usdz`等结构数据，现有capture.zip不应假设直接兼容。先审计输入转换与缺失信息，优先复用已有RGB/深度/位姿；确实缺少结构再补采集导出，不覆盖旧原件。

本轮没有修改上述源码。

## 六、几分钟等待怎样才可能成为目标

端到端等待必须计算：传输＋结构解析＋布局规划＋最长资产任务链＋组装＋必要照明处理＋导出＋下载。14个新资产并行仍受生成服务/GPU队列限制；不是开14个Agent就能让物品同时免费秒出。

| 路线 | 适用范围 | 几分钟目标的可信程度 |
|---|---|---|
| 模板/参数几何＋已有资产＋实拍纹理 | 规则家具和有限重点物件，复用多 | 可作为产品开发目标，尚无本机端到端计时 |
| 2–3件新重点资产＋其余复用 | 小范围初版，限制修订次数 | 可设时间预算，不能保证最终高清也同时完成 |
| 整屋新建14件复杂资产＋多轮校正＋高清烘焙 | 接近创作者展示片 | 当前证据不足以承诺≤5分钟 |

建议两个明确状态：

- **可交互初版**：房间、正确坐标、基础材质、重点部件和动作可用；未完成资产有明确标记。
- **精修完成版**：替换资产、修正材质和近景细节，保留对象ID和记忆；用真实数据确认耗时与质量。

渐进交付只是体验设计，不能用来回避用户对最终成片的时间要求。若用户不接受初版与精修分开，必须先通过真实范围证明最终版的时间再承诺。

提速优先级：选清晰视图并按需读取 → 资产去重/缓存 → 参数化结构 → 局部修改不重建全屋 → 限制新物品和重试 → 低成本预览后一次必要导出 → 移动端分级资源。不要每轮把188张原图重发给模型，也不要靠几十轮无约束截图反馈提高稳定性。

## 七、推荐实施顺序（方案，未执行）

1. 定义EvidenceBundle/SceneSpec/AssetManifest及来源、坐标、部件身份，扩展一个独立Blender-agent provider。
2. 固定LiteReality-Agent版本，核对采集格式与room_ops/agent/providers/model runtimes四个边界，不先全仓库接入云端默认项。
3. 用现有房间资料先覆盖桌面＋一柜门＋2–3个物件，优先真实/缓存资产；在此范围验证前置资产质量是否够后续交互。
4. 实现Blender结果到MemoryRoom适配：拆节点、保留ID、关节转换、初始相机、来源和版本；确定手机加载能力。
5. 以选定手机实际运行画面与多视角实拍比较，记录总耗时和成本。几何/材质/动作分别判定，不用一张最好看的截图代替完整结果。
6. 只有上述闭环稳定后，再扩大到整屋、更多Agent和更多资产生成商；Unity/原生客户端按需要接入。

验收应覆盖真实位置/尺度、近景关键物体、未拍信息标记、柜门开合无明显穿插、拿走后无固定重影、记忆绑定不随资产替换丢失、手机交互性能、取消/失败/部分完成状态、端到端时间和实际费用。上述为产品结果约定，不是在本轮编写或运行测试。

## 八、现在可以据实说什么

这条方向已有直接创作者案例，也有更对口的公开端到端工程；我们不必从一个裸BlenderMCP开始自造所有模块。最值得深审的是LiteReality-Agent，网页资产交付可参考img2interior工作流；小物品、真实几何约束、标准化导出与Agent能力差异仍是必须补的工程。

本次没有证据证明任意Agent均可同质量运行，也没有证据证明完整高清整屋分钟级完成。手机App免费、项目代码Apache、图片生成成本、Agent订阅和GPU开销是不同事项，不能合并成“永久免费全自动”。
