# MemoryRoom：walk-into-memory 项目借鉴评估

日期：2026-10-30。对象是 [xibihe/walk-into-memory](https://github.com/xibihe/walk-into-memory)，MIT 许可，2026-10-28 创建，评估时 6 星。本次通过 GitHub 接口读取了 README、第三方声明以及 `level.py`、`spz.py`、`pipeline.py` 的部分源码。没有克隆仓库、安装、运行，也没有把它的代码复制进本项目。

## 一、结论

**它是“把一张照片变成能走进去一小步的 3D 场景”，不是多视角重建整间房，也做不到拿起物品。** 主线没法照搬。但它有三处工程做法正好对上我们现有的问题：**地面找平**（对应成片竖直方向歪了约 49°）、**按贡献精简高斯并转 SPZ**（对应 236 MB 的成片），以及**逐个高斯的着色器动效**（对应想要的“游戏式”氛围）。另外，“老照片走进去”可以作为一个新的记忆功能方向，但它用的模型只限非商业用途。

## 二、它是什么、用什么框架

```text
单张照片 → Apple ML Sharp（单图预测高斯，约 118 万个）
        → pipeline/（Python）：裁画框外、保护人物、修细长高斯、找平地面、按贡献精简到 56 万、写 SPZ + JSON
        → app/（Swift / Metal，visionOS）：MetalSplatter 渲染 + 手势动效
```

| 部分 | 技术 | 许可 |
| --- | --- | --- |
| 照片 → 高斯 | Apple ML Sharp，单目前馈预测，不需要训练；不在仓库内 | 代码为 Apple 示例代码许可；**权重仅限非商业研究**，生成的场景可能同样受限 |
| 后处理 | Python：numpy、SciPy、OpenCV、PyTorch（CPU 即可）；Mask R-CNN 做人物蒙版 | MIT |
| 文件格式 | SPZ（Niantic 开源压缩格式）加 JSON 附带文件 | MIT |
| 渲染端 | MetalSplatter（Swift/Metal），每帧 GPU 排序，双眼立体；只支持 Apple Vision Pro | MIT，内置并修改 |
| 动效 | 浮现动画改编自 Spark（我们查看器用的也是 Spark） | MIT |

README 写明 `pipeline/` 和 App 的大部分代码由 AI 编程助手 Grok 编写。

## 三、与 MemoryRoom 的差异

| 维度 | walk-into-memory | MemoryRoom |
| --- | --- | --- |
| 输入 | 一张照片 | 多视角视频或照片，带 ARKit 位姿和深度 |
| 可动范围 | 原拍摄位置附近一小块；离得远或绕到背后就是 AI 猜出来的 | 在拍过的区域内自由走动 |
| 物品 | 整张图是一个场景，不分离物品 | 独立物品可拿起、归位；柜门可以开合 |
| 运行端 | visionOS 原生 App | 网页（Spark + Three.js），面向手机 |
| 记忆内容 | 没有 | 记忆卡片、附件、版本 |

## 四、可以借鉴的地方

### 4.1 地面找平：直接对应朝向问题

`level.py` 在可能是地面的点里随机抽 3 个点拟合平面（RANSAC），重复 600 次取支持点最多的那个，再用 SVD 精修法线，然后把法线旋到竖直方向，同时算出相机离地高度。

用到我们这里：

- 我们的成片 PLY 头里写着 `Vertical axis: -0.757 0.651 -0.058`，与 +Y 约差 49°，查看器没有读取。可以先用这个轴做粗校正，再在高不透明度的高斯中心里用 RANSAC 拟合地面，精确找平并确定地面高度。
- 我们有 ARKit 位姿，重力方向是已知的，比它的单张照片更可靠。找平应该作为 ARKit 对齐之后的校验或补充，而不是替代。
- 这段代码是 MIT 许可、50 行左右，借用时保留署名即可。

### 4.2 按贡献精简 + SPZ：对应 236 MB 的成片

做法：从 14 个附近视点渲染，累加每个高斯对画面的贡献，分几轮保留贡献最大的 N 个（默认 56 万）；再写成 SPZ，56 万个约 7–8 MB。

用到我们这里：

- 我们有训练用的 422 个真实相机，用这些视角计算贡献比它的 14 个假设视角更准确。
- 我们现在 100 万高斯、236 MB，已经接近 256 MB 的项目包上限。精简并转 SPZ 后，有望降到几十 MB，手机加载会快很多。具体能缩到多小、画质损失多少，要实测。
- **注意：它的 SPZ 写入只保留 SH0（颜色不随视角变化）。** 房间里的反光和高光会因此变平。我们应该用 Niantic 官方 spz 库或 PlayCanvas 的 splat-transform，保留 SH 再压缩。Spark 本身能读 SPZ。
- 它的精简跑在 CPU 上，README 说完整场景需要“很多分钟”。我们可以放在 Mac 或学校 GPU 上跑，作为导入前的一个步骤。

### 4.3 逐个高斯的着色器动效：对应“游戏式”氛围

它在顶点着色器里对每个高斯做浮现、伸手处消散、起风摆动和边缘呼吸。浮现动画来自 Spark，Spark 2 的 dyno 着色器系统在网页端也能实现类似效果。

可以用在：

- 进入空间时整体浮现，营造“回到记忆里”的仪式感。
- 拿起物品时，背景高斯变暗、变淡，突出手里的物品。这正是之前讨论的恐怖游戏式“检查物品”。
- 打开一张记忆卡片时，绑定的物品周围出现淡出或光晕。

这些都是表现层，不依赖重建质量，可以在现有成片上先做。

### 4.4 其他小技巧

- **JSON 附带文件：** 把相机高度、画框、风区等元数据和模型分开存放。我们的 `scene.json` 已经是这种做法，不需要改。
- **头动超过 1 cm 才重新排序：** 原生渲染器的性能技巧。Spark 有自己的排序策略，网页端是否需要，要看手机上的实测帧率。
- **修细长高斯：** 缩短沿视线方向的“针状”高斯，减少拉丝。我们的成片如果走近看有拉丝，可以参考。

## 五、一个新的功能方向：老照片走进去

很多人想回到的房间已经不在了，比如老家、旧宿舍，只剩下几张照片。单图生成高斯能让用户“走进”这些照片，哪怕只有一小步的范围，也很符合 MemoryRoom 的定位。

限制：

- ML Sharp 的权重只限非商业研究用途，不能放进产品。要做这个功能，得另找可商用的单图或少图生成模型，并重新核对许可。
- 画面外和物品背后都是 AI 推测的，必须标明“由照片推测”，不能当作真实扫描。
- 只能在原拍摄位置附近小范围移动，不能自由漫游，也不能拿起物品。

建议作为二期功能记录，不影响一期主线。

## 六、建议

1. **朝向问题：** 查看器导入时先读 PLY 的竖直轴，再参考 `level.py` 加地面找平；有 ARKit 数据时优先用 ARKit 重力对齐。
2. **成片体积：** 加一个“导入前精简”步骤，用训练相机计算贡献，保留 SH 再转 SPZ。和原始 PLY 并排对比画质。
3. **氛围动效：** 用 Spark 的 dyno 做“进入浮现”和“检查物品时背景变暗”，在现有成片上就能先做。
4. **老照片：** 记为二期方向，先调研可商用的单图模型。

前三项都要改代码，需要用户同意后再做。按 AGENTS.md 的约定，改完不会自行运行验证。
