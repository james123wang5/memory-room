# MemoryRoom：重建路线选型与椅子扫描

调研日期：2026-10-25。设备背景：M1 Pro / 16 GB、iPhone 17 Pro；优先本地、保留原始数据、可接入现有 Three.js / Spark 项目。此次只调研，未运行测试、训练、重建或第三方应用，未改应用代码。

## 决策

**房间本地重建主线选 OOOSplat；可移动物品主线选 Apple Object Capture 生成独立网格；Classic Scaniverse 作为手机成片备用入口。**

这是按设备适配、工作流完整性、使用成本、成片潜力与项目接入条件做出的选型，不是同一组素材实测得到的画质冠军。当前没有找到足以证明某个候选在我们的房间、手机和 Mac 上全面领先的独立对照。

建议将我们已有项目的重点保留在场景组织、交互、归位、内容、保存，以及原始素材管理；重建部分优先复用完整工具链。现有 ARKit 位姿直接送入 Brush 的简化流程降为备用。不要把当前较差的图片当作 Brush 画质上限，也不要把换工具视为必然修好所有原始素材。

检索分为五个方向：桌面本地工具、手机及商业采集、实际社区反馈、物品与遮挡、生成式补全。Exa 共请求 79 条候选结果（包含重复和不相关条目，不是 79 个独立证据）；公开原文优先用 Lightpanda 读取，GitHub 页面不足时用其公开 API。重点阅读官方说明、实际问题报告与官方采集指导；没有把排行榜转载当作效果依据。

### 为什么现阶段选 OOOSplat

最关键的差异是照片配准及完整处理流程。我们当前用 ARKit 记录的相机位姿直接构建数据集；OOOSplat 路线会从图像特征重建相机关系。这为修正多视图不一致提供了另一条路径，但纹理少、反光或素材模糊时，COLMAP 同样可能失败。它不是手机采集器，不能直接解决现场“哪里扫过了”的界面问题。

当前项目标准配置为 6000 步、最大长边 1024、最多 40 万高斯；OOOSplat 文档里的快速、均衡、精细档使用不同且更充分的处理预算。我们的配置是早期资源取舍，不是画质最优证明。提高分辨率或训练预算会增加时间和内存，也无法恢复根本没拍到的细节。

需更正上轮说明的精度：OOOSplat 是 Brush 系列工具链；当前 main 的 Mac 说明已写 OOOBrush 运行时，不能简单说它与我们固定的 Brush v0.3.0 完全相同。安装包能力应以具体发行说明为准，不能混用旧截图、main 文档和某个安装包的状态。[当前仓库](https://github.com/ooolabdev/ooosplat)、[发行说明](https://github.com/ooolabdev/ooosplat/releases)。

集成时仍有三项工程工作：COLMAP 输出的朝向和尺度不能直接当作原始 ARKit 米制坐标；高质量模型可能超过我们现有 256 MB 项目包限制；第三方高斯模型需要在现有查看器中保持相同的显示解释。最先复用的是原始照片、任务输出与模型导入，不是盲目覆盖整个 App。

### 示例和社区证据究竟说明什么

我读取了 OOOSplat 官方任务界面和模型预览图。任务界面把素材、目录、质量档及历史放在一起，确实方便；但截图标识是较旧的 Windows 0.3.0 / NVIDIA 环境。预览示例是室外街区，中心较清楚、周围有拉伸，不能据此断言我们的室内玻璃柜也能同样清楚，更不能推断 M1 Pro 的耗时。[任务界面](https://github.com/ooolabdev/ooosplat/blob/main/assets/screenshots/task-workspace.png)、[模型预览](https://github.com/ooolabdev/ooosplat/blob/main/assets/screenshots/gaussian-preview.png)。

OOOSplat 的真实问题区也反映了工作流边界：照片补拍特征提取问题 #61 调研时仍开放；PNG 特定焦距元数据处理问题 #73 有兼容处理，但维护者仍区分临时处理和底层修复。另一些诊断问题已经关闭，不能把所有历史问题说成当前版本仍有。[补拍反馈](https://github.com/ooolabdev/ooosplat/issues/61)、[焦距问题与处理说明](https://github.com/ooolabdev/ooosplat/issues/73)。

Scaniverse 社区有对近距离、背景参照、覆盖多个视角的具体讨论，说明易用产品仍依赖拍摄方法。这是现场经验，不是随机对照，也不建议照搬其中快速运动等不适合我们采集器的个人技巧。[社区拍摄问题](https://community.scaniverse.com/t/scanning-questions/1187)。

Postshot / SuperSplat 曾有同一 PLY 在不同查看器表现不同的公开案例，相关讨论后来有修复反馈。它说明比较时不能只看不同软件的截图，也不能据此断言当前 Spark 有同一个错误。[社区讨论](https://forum.playcanvas.com/t/postshot-to-supersplat/39376?page=2)、[相关历史问题](https://github.com/playcanvas/supersplat/issues/396)。

Teleport 发布过空间比较，有细节图和相同视点的说明，值得参考，但作者就是供应商，且没有覆盖所有候选及我们的设备；不能据此选出独立意义上的第一名。[供应商比较](https://get.teleport.varjo.com/blog/why-teleport-is-the-best-solution-for-capturing-places-in-3d)。

## 手机操作到底选什么

若目的是马上用成熟产品拍完并得到成片，Classic Scaniverse 的手机闭环更省事。官方目前仍说明经典体验保留免费手机处理；新 Scaniverse 的资产生成和空间服务采用另一套账户/额度体系。需要选择正确入口，而非笼统宣称所有 Scaniverse 服务永久免费离线。[当前官方说明](https://www.nianticspatial.com/en/pricing)。

若目的是让我们的产品以后可以持续接入、改流程和控制模型，OOOSplat 更适合做桌面重建主线；手机端独立处理采集指导。Stera 是 RGB、深度、位姿、IMU 等同步采集基础设施，apple-spatial-capture 是多种 Apple 能力的插件封装；它们可提供采集组件，但不能当作有独立画质优势的完整房间重建算法。[Stera](https://github.com/fpv-labs/stera-app)、[apple-spatial-capture](https://github.com/A7ALABS/apple-spatial-capture)。

## 椅子：可移动资产的正确拆法

### 先区分两个结果

房间模型负责展示原空间。独立椅子模型负责搬走、转向、拿近查看。只在整屋高斯中圈出一把椅子，最多得到原来观察到的表面；被墙挡住的椅背、座垫下面和后腿不会因此出现。删除背景中的椅子也不会还原它遮住的地板。

因此应在采集设计里把这两个素材分开：先保留椅子原位置和实际尺寸的信息；移走椅子，拍干净的地面、墙面；然后在空旷位置单独扫描椅子；最后将独立模型放回原位。若在另一段 ARSession 或另一处扫描，使用人工尺度/摆放或后续标记配准，不能假设坐标自动重合。

对“拿起并旋转检查”的目标，我建议独立椅子优先用有贴图的 Mesh / GLB；对外观优先的静态椅子，也可使用独立高斯并配简化碰撞体。这是交互工程取舍，不是说高斯绝对不能移动。

### 三档完整度：让用户有可完成的流程

| 目标 | 拍摄要求 | 使用效果与取舍 |
| --- | --- | --- |
| 正常摆放、搬开椅子 | 前后左右、斜上方、尽量补低角度；背景空位单拍 | 适合常规走动观看；不可宣称底面可任意翻看 |
| 拿起、翻转、检查底部 | 在上面基础上，增加底面片段并正确合并 | 接近完整独立资产；采集和配准成本增加 |
| 难拍、反光、黑色细腿 | 可见部分扫描，少量缺失手工补模或使用明确标记的生成式补全 | 可得到游戏可用模型，但补出的部分不能称为扫描事实 |

绕一圈只覆盖水平方向，并不等于所有表面都被看见。多数椅子需要高、中、低几组视点，扶手下方、椅腿内侧和座板底部另补。优先让椅子保持静止，相机移动；带轮或可转座椅先固定住容易运动的部分。

### 能不能把椅子翻过来拍

可以，但使用专门支持物品翻转/多姿态合并的流程。Apple Object Capture 明确提供分段拍摄和翻转引导；对不适合翻转的目标，建议不同高度采集。它也指出重复纹理、低纹理、透明、反光、细结构等情况有困难。可以从官方示例与系统采集 UI 开始复用，不必自己重写全部指导。Apple 底层能力是系统 SDK，并非一个完全开源的重建引擎。[官方讲解与示例入口](https://developer.apple.com/videos/play/wwdc2023/10191/)。

关键规则：每个片段内物品静止；改变姿态后进入新的物品扫描段，由物品重建流程匹配。**不能把翻转前后的照片继续当作同一个静止房间，直接沿用我们当前的 ARKit 世界位姿训练。** 对纹理足够且刚性的椅子，翻转分段可能合并；对纯白、对称、重复条纹或软垫变形的椅子，不能保证可靠。

更高级的摄影测量可以用物品蒙版排除背景，再配准物体本身。Agisoft 的转台教程说明了背景特征干扰与掩码处理；其空背景差分需要相应相机位置的背景图。不能把这当成我们自由移动手机时任意拍一张空地就能一键抠图的依据。[官方转台工作流](https://agisoft.freshdesk.com/support/solutions/articles/31000163268-turntable-capturing-scenario-and-processing-workflow)、[背景蒙版条件](https://agisoft.freshdesk.com/support/solutions/articles/31000162414-masks-from-background-photos)。

Apple 常见输出是 USDZ，我们现有网页直接接收的独立网格是 GLB；后续需要资产转换与方向/尺寸整理。不能把官方示例能导出 USDZ 说成已完成与我们的项目对接。

### 无法拍到的部分怎么办

若确实无法看到底面，就没有足够观测来证明底面真实形状。可以让该资产只支持正常摆放/搬动视角，或者补一个简单底面、隐藏内部结构、使用同款产品模型。必须允许 360 度翻看时，才投入完整补拍或补模。

SAM 3D Objects 等从单张图像估计遮挡物品的路线可作为生成式备用；它能输出独立物品是有价值的，但看不到的细节依赖模型推断。真实的榫卯、螺丝、底部织物、背部铭牌等不能保证一致。[Meta 官方介绍](https://ai.meta.com/research/sam3d/)。

KIRI 的对象遮罩与网格输出也能减少手工步骤，但它属于商业服务路线。应在明确接受服务端处理及套餐条件时再接入，不会在本轮上传数据。[KIRI 教程](https://www.kiriengine.app/tutorial/introduction-to-3dgs-scan)、[导出格式](https://www.kiriengine.app/features/export-formats)。

## 后续开发优先级建议

1. 房间：补 OOOSplat 素材导出/模型导回适配，保留原图、帧顺序和相机信息；导回时处理单位、坐标、文件大小。先以安装包为独立工具复用，具体内嵌方式再按稳定版本决定。
2. 采集：继续把现场指导做清楚，但不把色块刷绿当成画质结果；允许成熟采集工具生成的模型进入项目。
3. 物品：优先官方 Object Capture 采集/重建分支，随后补 USDZ → GLB、摆放和实际尺寸确认。
4. 背景：对需要移动的物品，明确要求空位素材；已有整屋模型中删除物品与生成干净背景是独立任务。
5. 难例：手工补模/现成资产优先作为可控兜底；生成式路线显示来源，避免把推断模型当作真实扫描。

本轮没有将以上任何方案安装、接入或运行。现状仍为第一批房间链路已跑通但质量未达标、第二批基础代码部分完成。该文件是选型依据与后续开发建议。
