Hi, thank you for open\-sourcing this project.

I noticed that the `open` authoring profile can access raw capture evidence through the evidence pack and measurement helpers. However, the current layout repair and room validation logic appears to focus primarily on internal geometric consistency, collision avoidance, support relationships, and simulation readiness.

When the initial reconstruction or RoomPlan estimates are inaccurate, both agent\-driven and rule\-based stages may move or resize geometry to resolve these issues. Although the resulting scene may become more physically consistent, it could also drift away from the original camera and RGB\-D observations.

Is there a plan to make RGB\-D observations a default constraint for geometry edits during the preflight and authoring stages, including both agent\-driven edits and deterministic rule\-based corrections?

Ideally, such a workflow could:
- require each wall, opening, or object pose/size edit to be supported by RGB\-D observations; 
- record the source frames, measurement method, and uncertainty for each edit; 
- validate edited geometry against held\-out camera frames using depth, silhouette, coverage, and free\-space consistency; 
- reject or roll back edits that worsen observation alignment; 
- treat missing depth as unknown rather than as evidence that geometry is absent; 
- separate observation\-grounded metric geometry from simulation\-only adjustments such as grounding or collision margins. 

The goal would be to let authoring correct inaccurate initial estimates while ensuring that the final scene remains consistent with the original camera observations.

Would an observation\-grounded editing and validation loop like this fit the project roadmap? If so, where would you prefer it to be integrated?

Hi Xuechun,

Thank you so much for raising this issue. I agree that grounding the layout agent and simulation readiness in real\-world captures is important for this task.

In fact, at the moment, we already have certain designs that are aligned with this principle. For example, the Layout Agent refers to the captured images when performing resizing and adjustments. The object\-supporting system is also grounded in the captured images.

We welcome any PRs on this, and we’ll evaluate them once submitted. If you’d like to contribute, you could integrate it into either:

```
├── 2. Layout agent
│   ├── merge objects that are built into each other, e.g. an oven that is built
│   │   within a cabinet; the two objects will be merged into one
│   └── make the layout simulation-ready with the multi-stage layout agent
```

or:

```
├── 6. QC checks
│   └── the quality gates the scene has to pass at the end
```

Please refer to this document for the overall structure:
[https://github.com/LiteReality/LiteReality\-Agent/blob/main/doc/modules.md](https://github.com/LiteReality/LiteReality-Agent/blob/main/doc/modules.md)

Many thanks,
Zhening
